09 · PhotonVision and our patches

PhotonVision, and how we made it better.

PhotonVision: the vision software.

The Jetson runs PhotonVision, the same free vision software many FRC teams use. This chapter shows what it does and how one camera frame flows through it. Ours is a special version: someone else's GPU version, merged with the newest official fixes, plus 34 small changes of our own. This chapter shows what PhotonVision does inside, where our copy came from, and every change we made.

What PhotonVision is

PhotonVision is open source vision software made for FRC. It runs on the coprocessor, reads the cameras, finds targets, and sends the answers to the robot. Robot code reads them with a library called PhotonLib, which looks the same whether the coprocessor is an Orange Pi or our Jetson.

You set it up from a web dashboard in your browser: pick a camera, choose a pipeline (a recipe for what to look for), tune the settings while you watch the live video, and calibrate the lens.

Each camera can switch between pipelines, and each pipeline type is a different kind of vision:

AprilTagCudaFinds AprilTags on the GPU with the 971 detector. What we run.
AprilTagThe same job on the CPU. Fine on a Pi, slower.

Object detectionA neural network finds game pieces. Ours runs on TensorRT.

Inside PhotonVision: one frame's path

Every camera gets its own VisionModule, and inside it a VisionRunner: a thread that loops forever, grabbing the next frame, running the pipeline on it, and handing the result on. Click any box to see what it does. The dots are frames.

Class names are PhotonVision's own (and the 4143 fork's AprilTagCudaPipeline). How results travel to the robot is chapter 15; the pose math is chapter 12.

Our AprilTag cameras use the AprilTagCuda pipeline, which hands detection to the GPU (chapter 08). Beside the pipelines, PhotonVision also records the cameras when the robot asks, reports the Jetson's health to the robot, and restarts a camera that stops sending frames.

Where our copy came from

Open source means anyone can copy the code, change it, and share their version. A copy that goes its own way is called a fork. Ours is a fork of a fork:

  1. PhotonVision (the official project, "upstream") runs AprilTags on the CPU.
  2. FRC Team 4143 made a 2026 fork that adds the AprilTagCuda pipeline, using the CUDA detector from FRC 971.
  3. We started from 4143's version, merged in upstream's newest 2026 release (v2026.3.4, our patch 00), and added patches 01–34.
  4. The detector itself is Austin Schuh's current code, built from 971's frc971/bos repo, with two patches and our own wrapper.

We don't copy their code into our repo. We keep patches: small files that say exactly what we changed (chapter 06 shows one), applied fresh at every build. That keeps the credit clear and makes it easy to take the next upstream fix.

Why 2026 software works with 2027 robot code

The robot runs 2027 alpha code, but the CUDA PhotonVision only exists for 2026. Porting it was rejected: 2027's libraries need a newer compiler and Ubuntu than JetPack 6 has. So we checked the source to make sure the two versions speak the same language. The key test: PhotonLib computes a hash of the result message's layout and refuses results whose hash doesn't match.

The one rule

Don't upgrade the robot's PhotonLib past the alpha-6 era. Upstream's alpha-7 changed timestamps to nanoseconds (#2566), which changed the message layout and its hash, and robot code would crash reading from this Jetson. NetworkTables and time sync are the same in both versions.

Building and installing it

Our build script (scripts/host/03-build-photonvision-fork.sh) runs on a laptop: it downloads 4143's fork at one exact commit, applies every photonvision-*.patch in order (what a patch is: chapter 06), and builds a single 76 MB jar in about 30 seconds. If a patch no longer fits, the build stops instead of guessing.

What we added: safe deploys

Once, a copy step moved only the first 228 KB of a 76 MB jar. PhotonVision couldn't start, and systemd gave up after 5 tries. Worse, we first believed it was fine, because we read a log line from the old process. Now 06-install-fork-jar.sh refuses any jar that isn't a valid zip, keeps the last working one as photonvision.jar.prev, and every check looks at the running process's own ID.

The best stories

Real engineering is mostly noticing that something is quietly wrong, finding out why, and proving the fix. These are our favorite examples.

photonvision-27 · reliability

Silently stuck at 320×240

At about 1 start in 20, two parts of the software raced to set the camera's video mode, and the camera ended up sending 320×240 while everything believed it was 1280×800. Our fast decoder noticed the size mismatch, but after 30 frames it fell back to cscore, which quietly stretched the tiny frames to full size. Detection kept running at 122 fps on a blurry image, using 1.7 cores instead of 0.5. No error anywhere.

Fix: a size mismatch never falls back. The frame is dropped, and after 1 s the camera is closed and reopened so the mode is applied again. The health check now fails any camera whose real format differs from what PhotonVision set.

photonvision-15 · speed

Stream only when watched

For the dashboard video, PhotonVision shrank, color-converted and drew boxes on every frame, 122 a second, even with no browser open. Now the stream thread gets a frame only while someone is watching, and at most 30 a second. Snapshots still work. With no viewer: 0.49 → 0.43 cores; with one: 0.52 → 0.47.

photonvision-13 · robot integration

Timestamps at mid-exposure

The robot needs to know when the picture was taken, so it can match it to where the robot was. The Linux driver stamps a frame when its first USB packet arrives. Our patch moves that back by half the exposure, to the middle of the time the sensor was collecting light. The robot code must not subtract it again. The camera's own delay before its first packet is still to be measured on the robot (chapter 14).

photonvision-29 · reliability

A stuck camera fixes itself

Once, after quick restarts, a camera sent only corrupt frames: 120 "invalid JPEG" warnings a second, and nothing reached the pipeline. Now a watchdog counts usable frames. After 3 s without one it reconnects the camera; 5 s later it resets it at the USB level, like unplugging it. In the bench test, TopRight was back 9.1 s after its frames stopped. (More failsafes: chapter 16.)

photonvision-30 · calibration & field

Calibrating the event's field

Real fields aren't built perfectly: a tag can sit a few centimeters off. On our Field Calibration page you push the robot to 10–20 spots and hold it still at each. The Jetson replays the recording through the same GPU detector, then solves every tag's real position and every camera's mount. On synthetic tests: tags to a few mm, camera height to 4 mm. The 3D view uses FIRST's own field CAD. (Shop test on real tags: still to do.)

Tap a tag to leave it out or bring it back.

photonvision-22 · calibration & field

Leaving out a bad tag

If a tag is mounted wrong at an event, one bad tag can drag every multi-tag pose off. Type its number on the Settings page (say 7, 12), or have robot code add it, and every camera's multi-tag solve ignores it. It's still reported as a target, dimmed. You list the bad tags, not the good ones. Click tags above to try it.

photonvision-25 · usability

Copy settings between cameras

Before, you photographed one camera's settings and typed them into the next. Now the pipeline menu has Copy settings from…: tick the groups you want, copy from any camera into this one, or into the same pipeline on every camera. Names, orientation and each camera's exposure limits are never copied, and resolution only between cameras that have the same video modes.

Bugs we found and fixed

None of this code was written for our exact setup, so we found real bugs. Each row is a story: what we saw, why it happened, what we changed, and what it taught us.

The pattern

Most of these weren't found by a crash. They were found because someone measured: a CPU number that seemed too high, a frame compared pixel by pixel, a memory graph over 8 minutes. When something works, it can still be quietly wrong.
