# Code audit, 2026-10-01

**Method.** Five independent reviews:
- the per-frame vision path;
- the server and dashboard;
- the native detector;
- install, system and tests;
- 2027 compatibility.

Every finding below was checked against the code, and each fix was tested where a test could reach it. The plan for 2027 is in [MAINTENANCE-2027.md](MAINTENANCE-2027.md).

New patches:
- `photonvision-62-2027-control-word`
- `photonvision-63-audit-fixes`
- `bos-09-candidate-quad-bound`

The other fixes are in `detector/`, `scripts/`, `tests/` and `tools/`.

## Fixed

### Would have hurt matches

| What | Found where | Fix | Checked by |
|---|---|---|---|
| **A 2027 robot looked permanently disabled.** WPILib 2027 publishes `/FMSInfo/ControlWord` (a struct), not `/FMSInfo/FMSControlData`, so PhotonVision never saw an enable. Idle mode held every camera at ~30 fps through auto and teleop, and quiet mode started 60 s after connecting. | `NTDriverStation` (patches 49, 56) | `photonvision-62`: reads both formats (2026 roboRIO and 2027 SystemCore). A robot whose control word never arrived counts as enabled. The struct needs a typed subscriber, because a table listener's untyped subscription is disabled for `struct:` topics. | `NTDriverStationTest` (fork), and `tests/fake-robot` in both formats (`FAKE_ROBOT_WPILIB=2026` or `2027`) |
| **A PhotonVision restart during quiet mode stopped every later match's recording.** Quiet mode makes the scratch partition read-only after a match. The next PhotonVision process (after a crash, a settings import, or Restart in the UI) started as "not quiet", so no enable made it writable again, and Rewind failed with "Read-only file system" until a reboot. Found 2026-10-01 by the SystemCore rehearsal (the fake cameras restart PhotonVision). | `QuietMode` (patch 56) | `photonvision-64`: at start-up, quiet mode takes over the real state (`/run/spectrum-quiet`, or the partition read-only) and leaves it as usual: at once with the robot disabled under 60 s, at any enable, or for a recording. `health-check.sh` fails if the partition is read-only while PhotonVision isn't quiet. | `tests/quiet-mode/restart.sh`, `tests/systemcore-rehearsal` (the match recorded after a restart) |
| **Quiet mode started a second after the robot connected, not after 60 s disabled.** At an event the Jetson boots on the date it last saved, then takes the robot's (patch 08): a jump forward of however long it was off. Quiet mode, and every other timer, measured intervals on the date. A jump back would have delayed quiet mode and frozen a frame-rate-limited camera (every Object Detection pipeline) for the size of the jump. Found 2026-10-01 (evening) reviewing the audit's open list. | `QuietMode`, `VisionRunner`, `IdleMode` and others (56, 50, upstream) | `photonvision-65`: every interval on `System.nanoTime`. | `tests/quiet-mode/clock-jump.sh` on the Jetson (date 1 h forward at +1 s): before, quiet at +1.0 s; after, at +60.2 s |
| **A failed exit from quiet mode left Rewind unable to record** for the rest of the event: PhotonVision called quiet mode off though the partition was still read-only, and never tried again. | `QuietMode` (56) | `photonvision-65`: it stays quiet, reports the error and retries every 5 s; `health-check.sh` fails. | `tests/quiet-mode/leave-fails.sh` (the block device made read-only) |
| **A Rewind counter lost to a power cut would have made the quota delete the newest recordings first.** The counter file is on the scratch partition and not synced. Names start with the number and name order is age order. | `RewindManager` (07) | `photonvision-65`: the number is never below the newest recording on disk. | `tests/rewind-sessions/run.sh` (counter rolled back to 1) |
| **A CUDA error outside `Detect()` aborted the JVM:** every camera down. This covered the mask upload, the graph recording and the far search. | `detector/GpuDetectorJNI.cc` | One guard around all of it. A failure skips the frame and rebuilds that camera's detector. A far-search failure turns only the far search off, for 10 s. | Regression corpus identical |
| **A busy scene could write past a 2048-entry GPU buffer** (candidate quads, no bound). | bos `apriltag.cc` | `bos-09`: 16384 entries, and a frame with more is skipped (ResourceExhausted), with no rebuild. The highest count seen is logged at each doubling from 512. | Regression corpus identical |
| **The optional GPU lock could deadlock every camera** against the graph recording's exclusive lock. | `GpuDetectorJNI.cc` | The lock is taken after the recording. | Code review (the lock is off by default) |
| **An exception outside `pipeline.run` ended that camera's thread** for good, with no report. | `VisionRunner` | The loop catches it, logs (rate-limited), sends a blank result and goes on. `VirtualMachineError` still propagates. | Laptop compile and tests; on the Jetson |
| **If the detector library failed to load, cameras 2 to 5 died.** Only the first caller got `UnsatisfiedLinkError`; later callers got `NoClassDefFoundError`. | `USBFrameProvider` | Both catches take `LinkageError`. | Code review |
| **On a fresh SSD the new partitions were never formatted.** blkid lists an empty partition by name, so "already formatted?" was always yes. Every fresh install stopped at the data-partitions step. | `10-data-partition.sh` | The decision uses the filesystem type (`blkid -p TYPE`). Lookups only search `$DISK`, and a duplicate name stops the script. | Re-run on the Jetson |
| **The boot fallback could cover a partition about to mount.** `nofail` mounts aren't ordered before `local-fs.target`, so after a power cut the fallback could run while fsck was still repairing. | `10-data-partition.sh` | The fallback unit is `After=` every data mount (ordering only). | Unit installed on the Jetson. **A real power-cut boot is still to do** (`tests/power-cut`). |
| **Match Ready could say READY beside USB FAIL lines** (they were counted in a subshell). | `health-check.sh` | Process substitution instead of a pipe. | health-check on the Jetson |

## Open (not fixed yet)

In rough priority order. None blocks the October event, but the first group is worth doing before it if time allows.

**Before October if possible**
- **Robot code camera names:** `Vision.java` still uses `orin-front`, `orin-left` and `orin-right`; the Jetson has `TopLeft`, `TopRight` and so on (issue #10, item 1).
- **Robot code contract**, documented in the README. [SpectrumVision](../robot-vision/README.md) (`robot-vision/`) now handles the `setEnabled`, excluded-tags and time-sync items, and alerts on a message-format mismatch. Still the robot code's job: camera names, and the event profile.
  - call `setEnabled(true)` at init: a camera disabled by robot code stays disabled across a robot-code restart;
  - filter `/photonvision/excludedTagsActive`: excluded tags are still sent as single-tag targets;
  - the event profile overrides a pipeline robot code set before the field connected;
  - results in the ~1 s after a NetworkTables reconnect can carry an unsynced timestamp (check `timeSinceLastPong`).
- **A power-cut boot test with the new fallback ordering** (`tests/power-cut/run.sh`, now able to fail).
- **Test on the SystemCore:**
  - the robot state on Match Ready, and fps while enabled (patch 62);
  - loop time with all cameras seeing tags.

**Native**
- Excluded tags still count toward the far search's "good view", so two excluded tags in view switch it off.
- Cameras at different resolutions break the far search's shared detector: it's rebuilt at each switch, and a detection's `family` pointer can be read after it's freed. Latent while every camera is 1280x800.
- Long holders of the shared CUDA lock (TensorRT engine load, detector rebuilds, the far-search warm-up) stall every camera when a graph recording is waiting.
- There's no watchdog for a `Detect()` that hangs.
- Smaller issues:
  - each non-fatal failure rebuilds the detector and re-records the graph;
  - a blocking `cudaMemcpy` in the GPU-input check;
  - unchecked `cudaMemcpy2DAsync` returns in `NvJpgDecoder`;
  - TensorRT decode with fewer than 5 output channels;
  - stats lines written in pieces, so cameras' lines can interleave.
- The detector setup is copied four times (the JNI, `fieldcal_detect`, `far_replay`, `far_search_test`). The 2x upscale uses two camera-matrix conventions.

**Java and server**
- After a pause in grabbing, the stuck-camera watchdog can reconnect a camera for no reason (a 0.5-1 s blackout).
- The CUDA pipe creates its detector at 640x480 and rebuilds it on the first frame. It keeps old intrinsics when a calibration is removed. The websocket thread can build the pipeline at the same time as the vision thread.
- With the read-only system on, the USB bandwidth cap and the radio switches aren't kept across a reboot (they live on the system partition).
- Field-cal `status()` does disk work while holding the lock every camera's frame thread needs (only during field calibration).
- Smaller issues:
  - snapshot pruning and field-cal Undo use the wall clock and names, not a sequence;
  - restore also replaces the network config and the field layout, which the UI doesn't say;
  - dashboard pollers have no in-flight guard or timeout;
- Rewind's `jetson_us` and `robot_us` are arrival times, not the mid-exposure timestamps the results carry (docs).

**System and tests**
- fstab still mounts by `PARTLABEL`, so a second disk with the same partition names (a cloned SSD in a USB enclosure) could be mounted instead.
- `02-flash-nvme.sh` doesn't check that its `nv-late-init.sh` patch matched. `--erase-all` has no prompt.
- The patched camera driver is lost silently on a kernel package update: hold the L4T kernel packages.
- `03-build-photonvision-fork.sh` downloads Node, Temurin and pnpm unpinned.
- The field-calibration solver doesn't check that it converged.
- Maintainability:
  - a shared `scripts/lib/common.sh` (sudo check, writable-root check, atomic install, ssh helper, test helpers);
  - `shellcheck` and `ruff` in CI;
  - one `tests/run-all.sh` where every test exits non-zero on FAIL.
