08 · CUDA and the GPU

Teaching 1,024 workers to paint at once.

A camera frame has a million pixels, and the Jetson has to find every AprilTag in it 120 times a second. The trick is to stop working on pixels one at a time and give every pixel its own worker. That's what a GPU is for, and CUDA is how we give it instructions.

One painter or a thousand?

Imagine painting a huge mural of small tiles. One master painter is fast but paints one tile at a time. A crowd of ordinary painters is slower per tile, but if each takes one, the wall is done in the time of one tile.

That's the difference between a CPU and a GPU. The Jetson's CPU has 6 cores: a few smart, fast workers that can each follow a complicated recipe. Its GPU has 1,024 cores: simple workers that are best when they all do the same thing to different pieces of data.

Try the race, then switch to a chain of steps where each tile needs the one before: the crowd can't help, and the master painter wins. A GPU is only fast when the work splits up.

Our AprilTag detector asks the same questions of every pixel, so thousands of GPU threads answer at once. Only reading the few tags' bits runs on the CPU. It takes about 1.7 ms a frame.

Analogy: grading tests

One teacher grading 1,000 multiple-choice tests takes all weekend. Hand one test to each of 1,000 students with the answer key, and it's done in a minute. It works because every test is graded the same way, and no test depends on another. Pixels are like that: "is this pixel brighter than its neighbors?" is the same question for every pixel.

Few smart cores, or many simple ones

A CPU core spends most of its chip area on being clever: predicting which way the code will branch, reordering instructions, and big caches so it rarely waits for memory. That makes one thread of complicated code run fast.

A GPU spends its area on more cores instead. The Orin Nano's GPU (NVIDIA's Ampere design) groups its 1,024 cores into 8 streaming multiprocessors (SMs) of 128 cores each. Every SM hands out one instruction to groups of 32 threads at a time, and all 32 run it together on their own data.

NVIDIA calls this SIMT: single instruction, multiple threads. One "brighten this pixel" instruction, 32 pixels brightened.

A kernel: one function, thousands of copies

A CUDA program is ordinary C++ with one new idea. You write a function called a kernel that says what to do for one pixel. When the CPU launches it, the GPU runs one copy per pixel, each copy on its own thread.

How does a thread know which pixel is its own? CUDA gives each one two numbers: threadIdx (its seat inside a small team called a block) and blockIdx (which block it's in). The blocks are laid out as a grid that covers the whole image. A thread multiplies them out to get its pixel's x and y.

This kernel is a simplified version of the first step of our AprilTag detector: make every pixel pure black or pure white.

// Runs once per pixel, all at the same time.
__global__ void threshold(const uint8_t* in, uint8_t* out,
                          int w, int h, int cutoff) {
  int x = blockIdx.x * blockDim.x + threadIdx.x;
  int y = blockIdx.y * blockDim.y + threadIdx.y;
  if (x >= w || y >= h) return;   // spare threads past the edge
  int i = y * w + x;
  out[i] = in[i] > cutoff ? 255 : 0;
}

// On the CPU: enough 16×16 blocks to cover the image,
// rounding up so the edges are covered too.
dim3 block(16, 16);
dim3 grid((w + 15) / 16, (h + 15) / 16);
threshold<<<grid, block>>>(in, out, w, h, 128);

Thread, warp, block, grid

  • Thread: one worker, one pixel. It has its own tiny private memory (registers).
  • Warp: 32 threads that the hardware moves in lockstep, like rowers on one boat. The SM issues one instruction per warp.
  • Block: a team of up to 1,024 threads that run on the same SM and can share a scratchpad (shared memory) and wait for each other.
  • Grid: all the blocks of one kernel launch. The GPU hands blocks out to its 8 SMs as they free up, so the same code runs on a small GPU or a huge one.

Block sizes are usually multiples of 32, so no warp is left half-empty. A block of 16×16 is 256 threads, which is 8 full warps.

When a warp disagrees: divergence

A warp has only one instruction pointer. So what happens at an if, when some of its 32 pixels are bright and some are dark? The warp runs both branches, one after the other. While the bright lanes do the if part, the dark lanes sit switched off, and then they swap. That's called warp divergence, and it's why GPU code tries to keep neighboring threads doing the same thing.

If every lane goes the same way, the warp skips the other branch entirely. Mixed lanes pay for both.

Where the data lives

Thousands of threads are useless if they spend their time waiting for data. A GPU has three main places to keep it, and they trade size for speed:

  • Registers: each thread's own few variables, right inside the core. Instant.
  • Shared memory: a small scratchpad inside each SM that the threads of one block share. A few times slower than registers, still very fast. Great when neighbors need each other's pixels.
  • Global memory: the Jetson's 8 GB of RAM. Huge, but a trip there takes hundreds of clock cycles. GPUs hide that wait by switching to another warp that's ready.

On a Jetson the CPU and GPU share the same RAM (unified memory), but the detector still keeps its own GPU-side copy of each frame, which costs one quick copy at the start.

Analogy: a classroom

Registers are the pencil in your hand. Shared memory is the table your group sits at. Global memory is the library across campus: it has every book, but you don't want to walk there for every word. Good GPU code walks to the library once, brings a stack of pages to the table, and lets the whole group work from it.

The CPU is the boss: launches and streams

The GPU never starts work by itself. The CPU (the host) tells it what to do: copy this frame over, run the threshold kernel, then the next kernel, then copy the answer back. Each command goes into a stream, a to-do queue the GPU works through in order.

Launching is quick: the CPU drops the command in the queue and carries on. When it needs a result (say, how many blobs were found, to size the next kernel), it has to wait for the GPU to catch up. The 971 detector does that about 8 times per frame. How the CPU waits (spinning in a loop, or sleeping until woken) turned out to matter less than we expected; see the four-camera story below.

How the 971 detector puts AprilTags on the GPU

The classic AprilTag library was written for CPUs. Austin Schuh of FRC 971 rebuilt its first half so that each step is either "one thread per pixel" or a standard parallel building block like sort, scan (running totals) or select (keep only the items that pass a test), from NVIDIA's CUB library. The part that isn't very parallel, reading each tag's bits, stays on the CPU. Scroll through it on a real camera frame from an FRC field: the 2026 blue outpost, with four tags. Chapter 02 showed what each step does; here the question is who does the work: thousands of GPU threads at once, or a few CPU threads.

1 · A frame arrives

A 1600×747 frame from a real FRC field. The first command copies it into the GPU's buffer. From here on we zoom in on tags 29 and 30, but every step runs on the whole frame at once.

Who works: one copy command, queued by the CPU.

2 · Threshold, at half size

The image is shrunk to half size (800×373 here) and cut into 4×4 tiles. Each tile's darkest and brightest pixel, spread to its neighbors, sets a local cutoff, so shadows don't matter. Pixels become white, black, or unknown (purple-gray) where the contrast is under min_white_black_diff, 20 in our tuning.

Who works: three kernels, fully parallel. One thread per 4×4 tile finds its min and max (16×16-thread blocks); then blocks of 256 threads sweep the ~300,000 pixels, each thread handling a few.

3 · Union-find: name the blobs

Connected pixels of the same color get the same label, so each white or black patch becomes one blob. A CPU would flood-fill, one pixel after another. On the GPU every 2×2 patch starts with its own label, and neighbors repeatedly merge labels (a union-find) until each blob has one name. Tiny blobs are dropped.

Who works: five kernels back to back, one thread per 2×2 patch. The hard part is that neighbors depend on each other; the merge passes let every thread work at once anyway.

4 · Blob boundaries

Wherever a black blob touches a white blob, record a boundary point tagged with that pair of blobs. A tag's black border against its white margin makes one long, closed boundary.

Who works: one thread per pixel writes points into a huge, mostly empty list. Then CUB "select" squeezes out the empty entries and a radix sort groups each pair's points. Sorting a million items is a classic GPU job.

5 · Filter and sort by angle

For each blob pair, CUB computes its extent: how many points, how big, where its middle is. Pairs that are too small or the wrong shape are dropped. The survivors' points are sorted by angle around the middle, so they go around the outline in order.

Who works: CUB reduce-by-key (one total per pair, computed in parallel), select, and another sort.

6 · Fit lines, find the corners

Along the sorted outline, fit a short straight line through each point and its neighbors and measure how badly it fits. On a straight edge the error is tiny; at a corner it spikes. The biggest spikes (peaks) are the corner candidates. The chart shows the error all the way around tag 29, computed on this frame's real pixels.

Who works: FitLines, blocks of 128 threads, one block per 240 points. This is the kernel that crashed on blank frames: zero points meant zero blocks.

7 · Fit quads

From the top peaks, the GPU fits four lines and intersects them into a quadrilateral: the tag's outline. Every blob pair is tried at once. What comes back to the CPU is a short list of candidate quads, not 1.2 million pixels. Shown: the four corners the AprilTag library found for each tag in this frame.

Who works: FitQuads on the GPU, then one small copy back to the CPU.

8 · Refine and decode, on the CPU

Only a handful of quads are left. Each one's edges are refined on the full-size image (using the lens calibration to straighten them), then the 6×6 grid of bits inside is read and matched against the tag36h11 list. Duplicates are removed.

Who works: the CPU, one task per quad on a pool of 6 worker threads. Four tags means four tasks: too few to be worth a GPU.

9 · Hand back to PhotonVision

IDs, corners and decision margins go back to PhotonVision, which works out each tag's 3D pose (chapter 12). On our Jetson the whole detector, steps 1 to 8, takes about 1.7 ms for a 1280×800 frame.

The detector's own stage list

The detector times itself with CUDA events between steps. From third_party/971apriltag/apriltag.cc in frc971/bos (the same code as RealtimeRoboticsGroup/aos frc/orin), in order:

Memcpy → Threshold (ThresholdAndDecimate: decimate, 4×4 block min/max, 3×3 filter, threshold) → Unionfinding (LabelImage: the Allegretti 2019 GPU labeling, kernels InitLabeling, Compression, Merge, Compression, FinalLabeling) → Diff (BlobDiff) → Compact (cub::DeviceSelect::If) → Sort (cub::DeviceRadixSort) → Bounds (cub::DeviceReduce::ReduceByKey) → Transform Extents → Filter by dot product → Filtered sort → Line Fit (FitLines) → Error Filter → Compress Peaks → Sort Peaks → Peak Extents → FitQuads. Then, on the CPU, DecodeTags runs RefineEdges (with lens undistortion), quad_decode_index and reconcile_detections on a worker pool.

The half-size search is hard-wired (CHECK_EQ(quad_decimate, 2)), which limits range for very small, far tags; docs/VISION-RESEARCH.md has our measurements. Corner refinement and decoding use the full-size image, so found tags keep full accuracy.

How fast, and where the speedup came from

We started with FRC 4143's copy of the detector (from about August 2024), then switched to Austin's current code from frc971/bos. In a side-by-side test on the same camera, the detection was identical and the time per frame fell from 2.4–3.0 ms to about 1.7 ms, 30–40% faster.

The A/B table shows something interesting: the new code alone ran at the same speed. The speedup came with Austin's recommended tuning, min_white_black_diff 20. More low-contrast tiles become "unknown" and are skipped, so fewer junk blobs reach the later stages. Measure, and you learn why something got faster.

At 1.7 ms, the detector could keep up with over 500 frames per second. The camera sends 120. So the GPU wasn't what limited our frame rate; chapter 10 is the detective story of what did.

The detector reports its own speed once a second, per camera. A real line from our Jetson, with 4 cameras running and nothing in view:

971 stats h1 1280x800: 122.405 calls/s, detect avg 0.905 ms max 1.487 ms, jni 0.004 ms, tags/frame 0 [bos]

Our PhotonVision's log, Sept 25, 2026. "calls/s" is the frame rate, "detect" is ms per frame (GPU stages plus the CPU decode). With no tag (a dark room) there's less to do: about 0.9–1.1 ms. With a tag in view it was 1.6–1.8 ms. Chapter 10 explains every field.

Real bugs, from our repo

None of this code was written for our exact setup. Here's what broke, and how we fixed it. Every fix is a small patch file (chapter 06 explains patches).

What we fixed: the sticky error flag

When a CUDA call fails, CUDA remembers the error in a flag that stays set until someone reads it. Newer versions of CUB check that flag before they start, and fail on any leftover error. One unchecked call early in the frame left the flag set, and a later, unrelated CUB step failed on every frame. Our fix (gpudetector-01) clears leftover errors between stages and logs which stage left one; the unchecked calls are now checked.

What we fixed: the blank frame

With nothing to detect (a covered lens, a dark pit, a plain wall), the detector computed 0 blocks and launched FitLines<<<0, 128>>>. A launch with zero blocks is an invalid configuration, and the error surfaced in the next CUB call on every blank frame. With the old watchdog, that restarted PhotonVision in a loop. bos-02 returns "no detections" early when no blobs survive. tests/detector-frame-sizes showed blank frames failing at 5 resolutions before, and passing at all of them after.

What we fixed: one GPU error took down everything

Austin's code stopped the whole program on any CUDA error, taking every camera with it. Now (bos-01) a failed frame is just skipped, and PhotonVision restarts only if the GPU itself stays broken for 1 s. The worst outage went from about 62 s to about 8 s; chapter 16 tells the whole story.

What we fixed: a slow leak

The old detector leaked two small matrices every time it decoded a tag. Tiny per frame, but at 120 frames a second over a long event it could run the Jetson out of memory. We applied Austin's upstream fix (3e570d5a), which is part of why we moved to his current code.

Four cameras, one GPU: waiting in line

With four cameras, the GPU was only about a third busy. Yet while the average frame took about 3 ms to detect, the slowest frames took 6 to 12 ms. How can a mostly idle GPU be slow?

It's the checkout line at a store that's mostly empty. Most of the time you walk right up. But every so often two or three people arrive at once, and someone waits. Each camera's frames arrive on their own clock, so sometimes one camera's GPU work lands just behind another's. The average stays low; the worst case doesn't.

Watch it happen. Add cameras and see the GPU line fill up and the slowest frames stretch out, even though the GPU is idle most of the time.

What we tried: more queues, and a sleeping CPU

CUDA funnels every stream into 8 hardware work queues by default, so one camera's kernels can wait behind another's even when the GPU has room. We raised it to 32 (CUDA_DEVICE_MAX_CONNECTIONS=32). We also let the CPU sleep while it waits for the GPU (cudaDeviceScheduleBlockingSync) instead of spinning in a loop. The first test made 32 queues look like a big win. Then we repeated it.

Lesson: measure more than once

The same settings varied by up to 2 ms from one restart to the next, more than the settings differed from each other. Averaged over all 11 runs, 32 queues were worth maybe 0.5 ms, and sleeping made no difference. Both are on anyway, because neither costs anything. And close the dashboard before you measure: 4 open camera streams added about half a CPU core and 1–2 ms to the slowest frames.

Neural networks share the GPU too

A GPU is good at anything made of the same small math repeated millions of times, and a neural network is exactly that. We run a YOLO model that finds game pieces (FUEL, for 2026) on the Jetson's GPU through NVIDIA's TensorRT, using the 2026 FUEL model by Team 2826 Wave Robotics. PhotonVision's Object Detection pipeline uses it like any other pipeline, and robot code gets normal targets with a class and a confidence.

But it shares the GPU with the AprilTag cameras. Uncapped, FUEL detection ran at 76 fps and pushed an AprilTag camera's worst detect time to 28 ms. So object detection is capped at 30 fps by default, where it has no measurable effect on the AprilTag cameras.

Chapter 8 recap
  • A CPU has a few fast, clever cores; the Orin Nano's GPU has 1,024 simple ones in 8 SMs, best at doing the same thing to lots of data.
  • A CUDA kernel runs once per thread. Threads come in warps of 32, grouped into blocks, which form a grid; blockIdx and threadIdx tell a thread which pixel is its own.
  • Warps run both sides of a mixed if/else, and data close to the cores (registers, shared memory) is much faster than global memory.
  • The 971 detector does threshold, union-find, boundaries, line fits and quads on the GPU, then decodes on the CPU: about 1.7 ms a frame.
  • We fixed sticky errors, zero-block launches, crashes and leaks, and learned to measure more than once before believing a speed-up.
