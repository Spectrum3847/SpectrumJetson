Linux, drivers, and why we patched one.Linux and drivers.

A computer is useless without the software that runs its hardware. On the Jetson that's Linux. Because Linux is open source, when its camera driver got in our way, we could read it, change it and build our own.Drivers are the parts of Linux that talk to hardware, like our cameras.

What an operating system does

Picture a busy restaurant kitchen. Lots of cooks (programs) want the stoves, the fridge and the one sink (the hardware) at the same time. Without a manager, they'd crash into each other. The operating system is that manager.

It decides which program runs on which CPU core and for how long. It hands out memory so programs can't scribble on each other's data. It talks to every device through drivers, so a program can say "give me the next camera frame" without knowing anything about USB.

Linux: free, and everywhere

Linux is an operating system anyone can download, read, change and share for free: it's open source. Linus Torvalds started it in 1991 as a hobby. Today thousands of companies and volunteers improve it together.

It runs almost every web server, every Android phone, most supercomputers, the SystemCore, and our Jetson. A "distribution" packages the Linux kernel with programs and tools; ours is Ubuntu, with NVIDIA's drivers added.

Why JetPack 6 and not 7?

JetPack 7 now supports the Orin Nano, but it moves to Ubuntu 24.04 and CUDA 13. Our CUDA AprilTag detector and the CUDA version of PhotonVision were built for JetPack 6. The newest version isn't automatically the best one: pick the one your software was built and tested on. 6.2.3 was the newest 6.x release, with bug fixes over the 6.2 in our original plan.

Kernel space and user space

Linux splits the computer into two worlds. The kernel runs in kernel space, with full control of the hardware. Everything else, including PhotonVision, runs in user space, where a program can only touch its own memory.

When a program needs hardware, it asks the kernel with a system call: "open /dev/video0", "give me the next frame". The kernel checks the request and does it. That wall is why a crashing PhotonVision can't take the whole Jetson down with it.

A driver is the part of the kernel that knows one kind of hardware. Here's how a frame reaches PhotonVision:

  1. The camera speaks UVC, the standard language of USB webcams. That's why it works without installing anything.
  2. The kernel's UVC driver, uvcvideo, collects the camera's USB packets into complete frames in memory.
  3. It hands them out through V4L2, Linux's standard video API, as the file /dev/video0.
  4. In user space, cscore (WPILib's camera library, inside PhotonVision) reads frames from that file.

Why we patched the camera driver

USB 2.0 splits every second into 8,000 slices of 125 µs called microframes. A camera streaming video reserves a fixed number of bytes in every single slice, like booking seats on a train that leaves every 125 µs. Its seats are guaranteed, even when it doesn't fill them.

We measured that the Jetson's whole USB 2.0 bus fits about 6700 bytes per microframe. The trouble: the stock driver books whatever the camera asks for, and a Thriftiest Cam always asks for the biggest booking, 3060 bytes (about 196 Mbps), in every mode, even though it only sends 4–7 MB/s. Two cameras fill the train. The third gets "No space left on device".

What we did: a one-knob patch

Our patch (kernel/uvcvideo-payload-cap.patch) adds one setting to the driver, payload_cap. For the Thriftiest Cam it caps the booking at 1280 bytes, still about 1.4× the largest frame we've measured at 120 fps. Tested with 2 cameras: 122 fps each, every frame complete. The price: results reach the robot ~2 ms later. Timestamps don't get worse, because the driver stamps a frame when its first packet arrives. The patch also counts each camera's bytes and largest frames for PhotonVision's USB bandwidth card (chapter 10).

The patch at work. Our script reads the driver's bookings. Four cameras on the USB-A hub book 3840 of the bus's ~6720 bytes.

Each Thriftiest Cam could book anything from 192 to 3060 bytes, and the stock driver would take 3060. Ours caps it at 1280. The two global-shutter cameras run at 60 fps and have per-port caps of 640, set from PhotonVision's Camera Matching page (chapter 10).

What a patch file is

A patch is a small text file that says "in this file, near these lines, remove these and add those". Lines starting with − are removed, lines with + are added, and the rest are context so the tool can find the right spot even if the file has shifted a bit.

This is the heart of our driver patch: after the stock driver works out how much bandwidth to book, we cap it. Switch between the diff and the code before and after.

  1. The file being changed: the stock driver's uvc_video.c (a/ is the original, b/ ours).
  2. The hunk header: "at line 240 of the old file (6 lines shown), which is line 273 of the new one (14 lines)". Our earlier hunks added 33 lines above this spot.
  3. Context: the stock driver's own last step, unchanged.
  4. Our addition: look up this camera's cap; if it asked for more, log it and book the cap instead.

Open source means you can fix it

With a closed driver, we'd have been stuck at two cameras, or had to buy different ones. Because Linux is open source, we read the driver, found the one number that mattered, and changed it: about 30 lines. Our whole project works like that: small patches to other people's code, kept as separate files so anyone can see exactly what we changed and why (chapter 09).

Building a kernel module

Most drivers aren't baked into the kernel. They're kernel modules: separate files (.ko) the kernel loads when a device shows up, like snapping a cartridge into a console. That's great for us: we can swap in our own uvcvideo without rebuilding all of Linux. scripts/jetson/11-uvcvideo-payload-cap.sh does it in six steps:

1. Fetchthe exact stock source for our kernel, v5.15.199

Step 3 is the safety check. A module must be built against the exact kernel it will run in, and NVIDIA sometimes changes drivers. If the stock source doesn't produce a byte-for-byte match of the installed driver (srcversion 51AFB22511907605800B082), the script stops instead of installing something subtly different. --undo puts the stock driver back.

The commands, and why GPL applies
# build against the running kernel's headers (M= is our folder)
make -C /lib/modules/$(uname -r)/build M=$PWD CONFIG_USB_VIDEO_CLASS=m modules
# the setting, applied every time the module loads
options uvcvideo payload_cap=1bcf:28c5:1280,32e4:0144:1280,32e4:62f0:1600
# swap the running driver (PhotonVision stops for a few seconds)
sudo modprobe -r uvcvideo && sudo modprobe uvcvideo
cat /sys/module/uvcvideo/parameters/payload_cap

Each payload_cap entry is vid:pid:bytes (a camera model) or port:bytes (the camera on one USB port, e.g. 1-2.4:944, set from PhotonVision's Camera Matching page). The setting is writable while running; a new cap takes effect the next time the driver sets the camera up, so PhotonVision applies it with a USB reset (about 2 s without frames).

The license. Linux is licensed under the GPL version 2. You may change it and share your changes, but anything you distribute that's built from GPL code must also be GPL, with its source available. So our patch is GPL-2.0, like the driver it changes, and it's published in our repo. That's the deal that keeps Linux open: everyone who improves it gives the improvement back.

systemd: the Jetson's stage manager

When Linux boots, the kernel starts one program, systemd, and systemd starts everything else: networking, logging, and services, programs that run in the background with no window. PhotonVision is a service.

A service is described by a small text file. The part we added tells systemd to restart PhotonVision whenever it exits, for any reason, one second later, and never give up:

# /etc/systemd/system/photonvision.service.d/90-spectrum-restart.conf
[Unit]
StartLimitIntervalSec=0
[Service]
Restart=always
RestartSec=1

systemd also feeds the Jetson's hardware watchdog: a timer on the chip that reboots the whole Jetson if Linux itself freezes for 30 seconds. Chapter 16 covers all our match-day safety nets.

From 57 seconds to 16.5

A robot is switched on moments before a match, so the Jetson has to boot fast. systemd-analyze told us where the time went: 45 seconds of every boot was snapd.seeded, a service preparing "snap" packages. We don't use any snaps. So we switched snapd off (masked it) and booted without the desktop.

Everything else we tuned

A laptop and a robot want different things from Linux. scripts/jetson/09-robot-tuning.sh makes ten changes (and --undo reverses them):

🚫

No automatic updates

Nothing may update NVIDIA or Java packages in the middle of an event.

🖥️

Headless

Boots to a text console, no desktop. Nobody looks at a screen on a robot.

⏱️

Clocks locked

jetson_clocks at every boot: CPU 1728 MHz, GPU 1020 MHz, so timing never wobbles.

🔌

USB autosuspend off

Linux likes to nap idle USB devices to save power. Cameras must never nap.

🔋

Power-cut safe

A robot is switched off, never shut down. Data reaches the SSD within 3 s (not 30), and the system log is kept on the SSD.

🌀

Fan at full speed

Noise doesn't matter on a robot: 56 → 43 °C.

🐕

Recover from hangs

30 s hardware watchdog, reboot 3 s after a kernel panic, PhotonVision always restarted.

😴

Idle threads sleep

OpenCV's helper threads spun in circles waiting for work. Now they sleep.

🔁

1 s USB retries

A stuck camera held up the others on its hub for ~65 s each. Now about 20 s.

📜

Bigger log

Up to 2 GB of system log, so the story of a bad match is still there afterwards.

Flashing: installing Linux on a Jetson

A new Jetson's SSD is empty. Flashing writes NVIDIA's operating system onto it, and updates the small boot program stored on the board itself. It's done from an Ubuntu 22.04 laptop over a USB-C cable, and took us about 7 minutes.

Recovery mode

Power off. Put a jumper on pins 9 and 10 (FC REC and GND) of the 12-pin button header under the module, not the 40-pin one. Power on, remove the jumper.

Connect

USB-C cable to an Ubuntu laptop. lsusb should list 0955:7523 NVIDIA Corp. APX: the Jetson is waiting in recovery mode.

Flash

Our script writes the OS to the SSD and the boot program to the board. "Waiting for target to boot-up" for 30 s is normal.

Wait for "Flash is successful"

Not the earlier "Successfully flashed the external device": the board is still writing then. Unplug too soon and you start over.
