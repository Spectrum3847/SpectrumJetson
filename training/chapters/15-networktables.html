15 · On the robot

Talking to the SystemCore.

The Jetson has found the tags and worked out where the robot is. None of that matters until the robot code hears about it. Here's how the answer travels down an Ethernet cable, and what the robot code does with it.

The Jetson plugs into the robot's network with an Ethernet cable: it's 10.85.15.15, the SystemCore 10.85.15.2. They share data through NetworkTables, WPILib's shared whiteboard. Every value has a named topic; programs publish or subscribe; the server, in the robot code, pushes each change to every subscriber. Every frame, PhotonVision publishes each camera's result (tags, corners, poses, timestamp) on /photonvision/<camera>/rawBytes.

Robot code reads it with PhotonLib: new PhotonCamera("TopLeft"), getAllUnreadResults(), a pose estimator, and addVisionMeasurement(pose, timestamp). Our cameras are named after the USB port they're in, because every Thriftiest Cam has the same serial number.

A cable and two addresses

The Jetson plugs into the robot's network with an Ethernet cable, the same kind of cable a desktop computer uses. The robot's radio acts as a small network switch, connecting the Jetson, the SystemCore and (over Wi-Fi) the driver station laptop.

Every device on a network has an IP address, like a street address for mail. FRC uses a pattern built from your team number: 10.TE.AM.x. We play as team 8515 at this event, so our addresses start with 10.85.15:

  • SystemCore: 10.85.15.2 (the .2 address is the robot controller's by convention)
  • Jetson: 10.85.15.15, a static address we set, so it never changes and never waits for one to be handed out

Data doesn't flow down the wire as one continuous stream. It's chopped into packets: small envelopes, each with a "from" and "to" address, sent one after another.

A packet is envelopes inside envelopes. Each layer is added by a different part of the system, and each is only read by the part that needs it. Step through them.

Ethernetthe hardware (MAC) addresses on this local network. A switch only reads it; a router would replace it.
IPfrom 10.85.15.15 to 10.85.15.2: the whole trip, Jetson to SystemCore.
TCPport 5810: which program on the SystemCore should get it, and a sequence number so lost pieces get re-sent.
NetworkTables"topic /photonvision/TopLeft/rawBytes now holds these bytes, as of time T".

Why layers? The switch in the radio only reads the Ethernet label. Routers read IP. The operating system reads TCP to find the right program. Only NetworkTables reads the innermost part. Nobody has to understand the whole thing, which is why the internet works.

A real detail: NetworkTables 4 actually runs its TCP connection as a WebSocket, the same technology web pages use for live updates. Time sync uses UDP on the same port number: faster, with no re-sending, which is fine for pings.

NetworkTables: a shared whiteboard

NetworkTables is WPILib's way for programs on the robot network to share values. Think of a whiteboard in the pit that everyone can see:

  • Each value has a name, called a topic, written like a file path: /photonvision/TopLeft/hasTarget.
  • A program that writes a topic is a publisher. A program that wants to know when it changes is a subscriber.
  • The whiteboard itself lives in the robot program on the SystemCore: the server. Everyone else is a client that connects to it on port 5810: PhotonVision, dashboards like Elastic, AdvantageScope.

When a publisher writes a new value, the server passes it on to every subscriber of that topic, with a timestamp. Nobody polls; changes are pushed. The robot code never has to know the Jetson's address. It just subscribes to the camera's topics.

Analogy

It's like a group chat with channels. You join the channels you care about, you post in the ones you own, and the server makes sure everyone in a channel sees each new message.

What PhotonVision publishes

Each camera gets its own folder of topics, named after the camera: /photonvision/TopLeft/…. The important one is rawBytes. Every frame, PhotonVision packs everything it found into one compact binary blob, a PhotonPipelineResult, and publishes it there. PhotonLib, on the robot, unpacks it.

Versions: the one rule

Our Jetson runs 2026 PhotonVision and the robot runs 2027 PhotonLib. That works because the message layout (its fingerprint hash) is identical in both, as we checked in the source (chapter 9). So don't upgrade the robot's PhotonLib past alpha-6: later versions changed the layout, and the robot code would throw an error reading from this Jetson.

What's inside a PhotonPipelineResult

Field names from PhotonVision's message definitions (photon-serde/messages.yaml, v2026.3.4). PhotonLib turns these into Java objects with getters like getYaw() and getBestCameraToTarget().

  • metadata: sequenceID (counts frames), captureTimestampMicros (when the light was captured, mid-exposure on our Jetson), publishTimestampMicros (when it was sent), timeSinceLastPong (how fresh time sync is).
  • targets, one per tag seen: yaw, pitch (degrees from the image center), area (% of the image), skew, fiducialId (the tag's ID), bestCameraToTarget and altCameraToTarget (the two candidate 3D poses of the tag), poseAmbiguity (how close those two are to each other in error: near 1 is bad, below ~0.2 is usually trustworthy), detectedCorners (the four corners in pixels), minAreaRectCorners, plus objDetectId / objDetectConf for game-piece models.
  • multitagResult (optional): estimatedPose (a best and an alternate field-to-camera pose with their reprojection errors and ambiguity) and fiducialIDsUsed. This is the multi-tag solve that uses every visible tag at once.

Four ports, four names

Here's a strange fact: every Thriftiest Cam reports the same name and the same serial number. To software, two of them are identical. So PhotonVision tells them apart by the only thing that differs: which USB port each is plugged into. We named the cameras after their ports, and the robot code uses the same names.

Swap two cables, swap two calibrations

A calibration belongs to one physical camera and lens. If TopLeft's camera ends up in TopRight's port, PhotonVision happily uses the wrong calibration and the wrong mount position, with no error. That's why the ports and cables get labels, and why the plugs get hot glue.

The Jetson's four USB-A ports, looking at them. Tap one.

Notice the hub numbers don't go in reading order: top-left is 2.1, but bottom-left is 2.2. That's how the Jetson's internal hub is wired.

The robot side: PhotonLib

Robot code uses PhotonLib to read the camera's results. The steps:

  1. Make a PhotonCamera with the camera's name. Ours are named after the USB port they're plugged into.
  2. Make a PhotonPoseEstimator with the field's tag layout and where the camera is mounted on the robot (robotToCam).
  3. Every loop, read getAllUnreadResults(). At 120 fps, 2–3 results pile up between 20 ms loops, and you want all of them.
  4. Turn each result into a robot pose: multi-tag first, falling back to the single tag with the lowest ambiguity.
  5. Hand it to the drivetrain's pose estimator with its timestamp. That timestamp is already on the robot's clock (chapter 14).

Real robot code also sets how much to trust each measurement (standard deviations), and rejects bad ones (too far, too ambiguous, off the field). That's in our robot code's vision subsystem.

// Once, when the robot starts
PhotonCamera cam = new PhotonCamera("TopLeft");   // = its USB port
Transform3d robotToCam = new Transform3d(
    new Translation3d(0.30, 0.25, 0.45),   // m: fwd, left, up
    new Rotation3d(0, Math.toRadians(-20), 0)); // tilted up 20°
AprilTagFieldLayout layout =
    AprilTagFieldLayout.loadField(AprilTagFields.k2026RebuiltAndymark);
PhotonPoseEstimator estimator =
    new PhotonPoseEstimator(layout, robotToCam);

// Every robot loop (every 20 ms)
for (PhotonPipelineResult result : cam.getAllUnreadResults()) {
  Optional<EstimatedRobotPose> est =
      estimator.estimateCoprocMultiTagPose(result);
  if (est.isEmpty())
    est = estimator.estimateLowestAmbiguityPose(result);
  est.ifPresent(e -> drivetrain.addVisionMeasurement(
      e.estimatedPose.toPose2d(),
      e.timestampSeconds));   // capture time, robot clock
}

Checked against PhotonLib v2027.0.0-alpha-2 (the PhotonPoseEstimator(layout, robotToCamera) constructor and the estimate…Pose methods) and WPILib's 2026 field list. The mount numbers are made up. In WPILib's Rotation3d, positive pitch points the camera down, so a camera tilted up has a negative pitch.

The other direction: robot → Jetson

NetworkTables works both ways. The robot code doesn't just listen; it also tells the Jetson things.

🕐

The time

The robot is the time sync server (UDP 5810), so Jetson timestamps can be converted to robot time. It also publishes its date on /photonvision/clock/unixMs so the Jetson's logs and recordings get real dates.

Record Rewind

Set /photonvision/rewind/record true and every camera is saved to the SSD. Our robot code will do it for each FMS match, named by the match (in progress).

💤

Rest while disabled

camera.setEnabled(false) stops a camera's processing, so the Jetson runs cooler while the robot waits for a match. A robot-set FPS limit does something similar.

🎚️

Switch profiles

Every camera has the same pipelines at the same numbers (say 0 = event field, 1 = practice field). Robot code can switch them all with setPipelineIndex, and the log records which was active.

📐

Where each camera is

Robot code publishes each camera's mount, robotToCamera, from CAD. Field calibration uses it, and sends back the measured mount on fieldcal/robotToCamera.

🚫

Leave out a bad tag

If a tag is mounted wrong at an event, robot code can list it on /photonvision/excludedTags, and every camera's multi-tag solve ignores it.
