16 · On the robot

Built for match day: failsafes and watchdogs.

A match lasts two and a half minutes. There's no time to open a laptop, and nobody can reach the robot. Whatever breaks has to fix itself, fast, or at least tell you exactly what to do in the pit.

Static shocks, loose cables, brownouts, power cuts and software bugs all happen on a robot, so every failure needs something that notices it and a fast path back. A camera that's unplugged and plugged back in is detecting again in about a second. A GPU error skips one frame, and if the GPU stays broken, PhotonVision exits and systemd restarts it in a few seconds.

The last line of defense is a watchdog: a hardware timer that systemd "pets" regularly. If Linux freezes and the petting stops for 30 s, the board resets itself and is finding tags again about 20 s later.

Assume things will go wrong

A robot is a rough place for a computer. It gets hit, shaken and zapped. Static shocks, loose cables, brownouts, power cuts (every robot power-off is one), overheating and software bugs all happen.Here's what we plan for:

  • Static shocks that glitch a USB connection
  • Loose cables after a hard hit
  • Brownouts: the battery voltage sags when motors pull hard
  • Power cuts: the robot is switched off, never shut down properly, so every power-off is a power cut
  • Overheating inside an enclosed robot
  • Software bugs: crashes, hangs, GPU errors

The engineering question for each one is the same: what notices it, what fixes it, and how long is vision gone?

~20sfrom power-on to detecting tags (the boot takes 16.5 s: chapter 6)
~1sfor an unplugged camera to be detecting again after it's plugged back in
8sworst-case vision outage after the GPU breaks
1.4sof video lost when we pulled the power mid-recording, with no filesystem errors

The watchdog: a dog you have to keep petting

What if the whole computer freezes? A frozen program can't notice that it's frozen. So you need something outside it: a watchdog.

Picture a guard dog that needs a pat every few seconds. As long as someone keeps petting it, it's happy. If the petting stops for too long, it barks and wakes everybody up. On the Jetson, the "dog" is a tiny timer built into the chip's hardware. systemd, the program that runs Linux's services, "pets" it regularly. If Linux locks up, the petting stops, and after 30 seconds the hardware resets the whole board. No software has to be working for that to happen.

Staterunning

A kernel panic (Linux hits an error it can't survive) is quicker: we set kernel.panic=3, so it reboots itself 3 s later instead of sitting frozen until the watchdog fires.

What we set, and a naming lesson

Our file /etc/systemd/system.conf.d/zz-spectrum-watchdog.conf sets RuntimeWatchdogSec=30s. NVIDIA ships its own file there that sets 120 s. systemd reads the files in alphabetical order and the last one wins, so ours is named zz- to be read last. We also set RebootWatchdogSec=30s: a reboot that hangs now resets itself after 30 s. It used to be 10 minutes.

    The 62-second restart

    Austin's detector used to stop the whole program on any GPU error. That triggered Ubuntu's crash reporter, which spent 28 seconds writing a 156 MB crash file before PhotonVision could even begin to restart: about 62 s without vision. Now a single GPU error skips one frame. Only if the GPU is broken for a full second does the detector exit cleanly (_exit, with JVM core dumps turned off), and systemd restarts PhotonVision. Worst case: about 8 s.

    Keeping an eye on it

    Before a match: health-check.sh is a readiness report you run over SSH. It checks everything this chapter talks about and prints PASS, WARN or FAIL for each: is PhotonVision running, is the GPU detector loaded, is every camera streaming at the resolution it was set to, is the fan really spinning (it reads the fan's speed sensor, not just what the fan was told), are there filesystem errors, is Wi-Fi off?

    During a match: the same health goes to the robot on NetworkTables once a second, so the robot code can log it and raise alerts. The throttle topic explains why the Jetson is throttling (slowing itself down): OVER-CURRENT when the supply sags, HIGH TEMP, or a capped clock.

    After a match: every camera's full settings are in the robot log (settingsJson), so you can tell what a camera was set to in any match. And Rewind video shows what each camera actually saw.

    Fast boot
    
  
    If anything does reset the Jetson, how fast it comes back is what matters. Our tuning cut the boot from 57 s to 16.5 s (how, in chapter 6); tags are detected about 20 s after power-on.
    
  

  
    Power cuts, recordings and the SSD
    
  
    
    
    
      
    A computer that loses power while writing a file can corrupt it, or corrupt the whole disk. Our defenses:
    
      
      
        
    • The filesystem (ext4) keeps a journal: it notes what it's about to change before changing it, so after a cut it can finish or undo half-done changes.
      • 
        
    • Written data reaches the SSD within about 3 s (Linux's default waits up to 30 s).
      • 
        
    • The system log is kept on the SSD across power cuts. It used to live only in RAM, so a brownout erased its own evidence.
      • 
        
    • Rewind forces its video files to the SSD every 2 s.
      • 
      
    
      
    The power-cut test
    We pulled the plug 21.4 s into a bench recording. After reboot: 0 filesystem errors, the log survived up to 3 s before the cut, PhotonVision came back healthy with both calibrations, and the recording kept 20.0 of 21.4 s. 1.4 s lost, and every saved frame was a complete JPEG (tests/power-cut/run.sh).

    Known issues: what we haven't beaten yet
    
  
    Real engineering includes the problems you haven't solved. Here are ours, written down honestly, with what we do about them.
    
  
    A USB glitch can leave a Thriftiest Cam stuck until its power is cut
    When the Jetson's USB hub resets while the cameras stay powered (a static shock can do this), both Thriftiest Cams stop answering. Other cameras come back by themselves in about 40 s. Nothing in software revives the Thriftiest Cams: not switching the port's power off (the hub says it can, but the board's 5 V is always on), not resetting the USB controller, and not rebooting the Jetson, because a reboot doesn't cut USB power. Replugging the camera, or power-cycling the robot, does. So the camera's health/problem topic says exactly that: "not answering on USB port 1-2.1: replug it, or power-cycle the robot."
    
  
    A software reboot hung twice
    After sudo reboot, the Jetson reset but never finished booting until it was power-cycled. The second time, both Thriftiest Cams were stuck. We suspect the boot firmware waiting on the stuck cameras, but haven't confirmed it. A hang in the boot firmware happens before Linux starts the watchdog, so the watchdog can't catch it. Rule for now: if cameras are stuck, power-cycle instead of rebooting. Next step: repeat the test with a monitor plugged in to see where the boot stops.
    
  
    Lessons
    Test long, not just fast: a memory leak only showed up after minutes of running (chapter 10). Quiet failures are the worst: a camera silently ran at 320×240, upscaled, at full fps, with no error anywhere. Don't let errors drown the log: one camera failure once wrote 20,000 log lines a minute, pushing out the history you'd need to debug it. Each of these is now caught by a patch and a check.
