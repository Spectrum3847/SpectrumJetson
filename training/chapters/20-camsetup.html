Setting up a camera.

A new camera, or one that replaces a broken one, from the box to poses you can trust on the robot. Nine steps, each with a number to hit. The why is in earlier chapters; this is the how.

Every step says where to click in our PhotonVision (at http://10.85.15.15:5800 on the robot, or 192.168.55.1:5800 over the USB-C cable on the bench), what "done" looks like, and which chapter explains it. Do them in order: later steps depend on earlier ones. Focus changes the calibration, and the calibration is needed for 3D.

It's written for a Thriftiest Cam, the OV9281 camera we run at 1280x800 MJPEG, about 120 fps. A different camera model works the same way, with its own numbers.

1

Plug in and name it after its port

Every Thriftiest Cam tells the Jetson the same name and the same serial number. So PhotonVision can't tell two of them apart by asking. The only thing that's different is which USB port each one is plugged into. That's why our cameras are named after their ports, and why a name, its settings and its calibration all stay with the port.

NamePort (looking at the Jetson's USB-A ports)Hub port
TopLefttop row, left2.1
TopRighttop row, right2.3
BottomLeftbottom row, left2.2
BottomRightbottom row, right2.4 (expected)

The hub numbers don't go in reading order. That's how the hub inside the Jetson is wired. Linux writes them as 1-2.1 and so on, which is what you'll see in logs and on the Camera Matching page.

  • Plug the camera into its port. Open Camera Matching in the sidebar.
  • A camera PhotonVision has never seen in that port shows as Unassigned. Press Activate.
  • On the Dashboard, press the pencil next to the camera's name (Edit Camera Name) and type the port name exactly: TopLeft, not topleft.
  • Label the cable and the port (chapter 16).

Robot code finds the camera by that name: new PhotonCamera("TopLeft"). Names are case-sensitive. If robot code asks for a name PhotonVision doesn't have, PhotonLib reports an error on the Driver Station and lists the camera names it did find.

Pass: the camera shows Active on Camera Matching, with its port name. Names on NetworkTables: chapter 15
The swapped-cable trap

PhotonVision matches a camera to its saved settings by port. Swap two Thriftiest Cams' cables and each one gets the other's name, settings and calibration. The Camera Matching page can't warn you, because the two cameras look identical to it. (It does show Mismatch if a different model, with a different name, lands in a port.) Robot code then applies the wrong mount to each camera, and the poses are wrong by far more than any calibration error. Try it in the lab below.

In this lab, robot code says TopLeft is the front-left camera, TopRight the front-right, and so on (example mounts, not our robot's). Each camera sees a tag 3 m ahead. The lenses really differ: TopLeft's calibration puts the image centre at x = 650.5 px and TopRight's at 597.9 px, so using the wrong one turns every direction by about 4°. At 3 m that's about 21 cm. Recalibrating fixes the lens, but never a swapped mount: only the right cable fixes that. "Heading from the gyro" is the solve our robot uses for its position (chapter 13): a swapped camera looks for its tag in the wrong direction, so the robot lands metres away. "Full pose" lands close, but facing the wrong way.

Replacing a camera? Plug the new one into the same port and PhotonVision gives it the old camera's name, settings and calibration, without a word. The name and settings are what you want. The calibration isn't: it belongs to the old lens. Always do steps 4 and 6 again for a replacement.

More on Camera Matching
  • How matching works: PhotonVision saves each camera with its USB path, a name under /dev/v4l/by-path/ that includes the port number (like …usb-0:2.1…). On start-up it opens each saved camera by that path. A camera shows Mismatch only if the name, USB vendor/product ID or path differ from what was saved, and two Thriftiest Cams share all but the path.
  • Deactivate stops using a camera but keeps its settings, so you can unplug it without the log filling with errors. Activate brings it back.
  • Delete throws away the camera's settings and its calibration, and can't be undone. Export the settings first (step 9).
  • A different model in a Thriftiest Cam's port (a Global Shutter camera, say) shows Mismatch, and PhotonVision still tries to run it with the saved settings. Put it back in its own port, or delete and set it up fresh.
2

Check it fits on USB

All the Jetson's USB 2.0 ports share one bandwidth budget, about 6700 bytes per microframe, and the USB-C port doesn't add any. With the stock camera driver, each Thriftiest Cam reserves about 196 Mbps and only two fit. Our capped driver cuts that to 82 Mbps each, so four fit on the USB-A ports.

  • On Camera Matching, look at the USB bandwidth card at the top: one bar for the whole budget, one colour per camera.
  • For each camera read Using (a share of its allocation) and Largest frame ("fits 1.4x").
  • A camera that won't stream at all ("Not enough bandwidth" in the kernel log): lower another camera's Allocation first, then raise this one. Each change resets that camera for about 2 s.
Pass: every camera streaming, none "squeezed" (Using under 90%), largest frame fits 1.3x or more. Why: the bandwidth lab in chapter 10
From the command line

scripts/jetson/health-check.sh says which camera driver is loaded (it must be the capped one for four cameras) and runs scripts/jetson/usb-bandwidth.py, which lists what each camera reserves, which ports failed and why, and the exact cap command to install if something doesn't fit. Allocations set on the page are saved per port and survive a reboot.

The defaults apply only to a camera with no saved pipelines: a port PhotonVision has never seen. 4

Focus the lens, then lock it

A Thriftiest Cam's lens screws in and out. Turning it changes focus and the calibration, so focus first and lock it before you calibrate.

  • Open Camera in the sidebar and find the Focus card. Turn on Measure.
  • Point the camera at something detailed that stays still, like a tag or the calibration board, about as far away as the tags you care about most.
  • Press Reset. Turn the lens slowly past its sharpest point, then back until Centre reads 100%.
  • Check the 3x3 grid. Each part of the image is scored against its own sharpest.
  • Lock the lens with glue or silicone.

The score depends on the scene and the light, so only compare numbers while nothing moves. A corner well below 100% while the centre is at 100% means the lens is tilted or that corner is soft; try another lens before you calibrate a bad one. The score is measured only while Measure is on, about 5 times a second, away from the vision thread.

Pass: centre at 100%, the grid close to 100% everywhere, lens locked. Why focus matters: chapter 3
5

Quick-check the exposure

The defaults are a good start: 5 ms exposure, cutoff 15. The main rule is short exposure on a robot. Auto exposure, or tuning by eye with the robot standing still, picks long exposures that blur as soon as it moves.

  • Follow the Tuning guide on the camera's Input tab: what to set, in order, with our values. Each control's tooltip starts with its recommended value.
  • Hold a tag at your far distance. Watch its decision margin in the Targets tab. It should sit well above the cutoff.
  • At an event, run tests/flicker-check/run.sh under the real lights. If frames pulse by several percent, go to exposure 83 (8.3 ms).

At an event, the Field Calibration page can tune each camera under the field's lights: turn the robot so that camera faces tags near and far, press Tune, then Apply recommended. It picks the shortest exposure that still finds every tag.

Pass: tags found at your far distance without flickering in and out; still about 120 fps. Why: chapter 4
6

Calibrate

A calibration belongs to one camera, one lens and one resolution. Do it after the lens is locked, at 1280x800, the resolution the camera runs at.

  • On the camera's page, in Camera Calibration, pick 1280x800. The board settings already match our board: ChArUco, Dict_5X5_1000, 30 mm squares, 22 mm markers, width 12, height 9. (The board says "9x12". 9x12 fails with "Negative corner in reprojection error calc".)
  • Press Start Calibration. In the card, set Auto Exposure off and Exposure about 150: calibration has its own exposure, and its default is nearly black.
  • Press Auto Snapshots (1 per second) and keep moving the board slowly. Cover every corner of the image, tilt up to about 45°, and change the distance.
  • Take at least 100 snapshots, then Finish Calibration.

When the calibration is saved, 3D and multi-tag turn on by themselves for that resolution. You don't need to touch the Output tab.

Pass: mean error under 1 px (under 0.5 px is great), few outliers, fx near 737 px. Why and how: chapter 11

Our bench calibrations: TopLeft 0.87 px, TopRight 0.97 px. Both found fx at about 737 px, so a Thriftiest Cam that comes out far from 737 went wrong somewhere. Outliers are the better warning: one early try had 42% outliers, because many snapshots had the board mostly outside the image. For the edges, keep most of the board in view and just touch the edge.

When calibration goes wrong
  • Stuck or failed: restart PhotonVision (Settings → Restart Software) to clear the bad snapshots, then start again.
  • Nearly black image: you forgot the exposure in the calibration card.
  • Check it: tests/calibration-check/check_calibration.py reads the saved calibration and reports the error, outliers and coverage.
  • 8 distortion numbers: the calibration fits 8 distortion coefficients. Our GPU detector uses all 8 (photonvision-04); its stock interface only took 5 and dropped the rest. PhotonLib's getDistCoeffs() hands the robot all 8 too.
  • Keep the calibration exposure out of the pipelines. 15 ms is fine for a board held still, and a blur disaster on a moving robot.
7

Measure the mount: robotToCamera

The robot needs to know where each camera sits, to turn "where the camera is" into "where the robot is". That's a Transform3d called robotToCamera in robot code, one per camera: how far forward, left and up the lens is from the robot's centre on the floor, and how it's turned. Chapter 19 has the axes and signs.

  • Take it from CAD, or measure with a tape: x forward, y left, z up, in metres.
  • Cross-check with the tags. With the robot level on the floor and 2+ tags in view, the Dashboard's Targets tab shows a Camera mount estimate: height, pitch and roll, averaged over 100 samples with a ± spread. The numbers use robotToCamera's signs, so negative pitch means tilted up.
  • Robot code publishes each camera's mount at /photonvision/<camera>/robotToCamera, so the Jetson can compare.
Pass: the estimate agrees with robot code within a centimetre or two of height and about a degree of pitch and roll. Why a degree matters: chapter 13

A degree is worth caring about: 1° of pitch error at 5 m moves the pose about 9 cm. The estimate only finds height, pitch and roll, because those are the same wherever the robot stands. Forward, left and yaw also need the robot's pose. The Field Calibration page finds all six: push the robot to 10–20 spots, press Solve, and the results compare each camera's mount with robot code's and give a Java snippet. The solved mounts come back on /photonvision/<camera>/fieldcal/robotToCamera (chapter 11).

8

Copy the settings to its siblings

Once one camera is tuned, don't retype its settings on the others (photonvision-25).

  • On the Dashboard, open the camera you want to fill in. In the pipeline menu (☰ next to the pipeline name), choose Copy settings from….
  • Pick the tuned camera and pipeline. Tick the groups: Camera, AprilTag, 3D and multi-tag, Resolution, Object detection.
  • Or copy into the same pipeline number on every other camera at once.
  • Check it worked: /photonvision/<camera>/settingsJson on NetworkTables holds each camera's full settings as actually set.

Never copied: orientation, names, and each camera's exposure limits. Resolution only copies between cameras with the same video modes. Calibration is never copied: every camera needs its own from step 6. The settingsJson topics are also recorded in every robot log, so after a match you can see exactly what each camera was set to (photonvision-24).

Pass: the two cameras' settingsJson match, apart from name, calibration and orientation. Our patches: chapter 9
9

Final checks, then back up

  • Frame rate: the Dashboard shows about 120 fps for a Thriftiest Cam at 1280x800 (we measured 122). Close other camera streams first: each open stream costs CPU. Robot code sees the same on /photonvision/<camera>/health/fps.
  • Distance: tags found, steadily, at the nearest and farthest distances you care about.
  • Pose: put the robot on a spot you measured with a tape. Each camera's pose should land where the robot really is, and all cameras should agree with each other. Turn the robot: the pose should turn with it, not jump.
  • Field layout: the Settings page says 2026 Rebuilt AndyMark, the same layout robot code uses. The excluded-tags box is empty, unless a tag at the event is mounted wrong.
  • Back up: Settings → Device Control → Export Settings saves every camera's settings and calibration in one file. Keep it on the team drive.
Pass: ~120 fps, tags at every distance you need, poses where the robot really is, settings exported. From corners to pose: chapter 12

For the whole Jetson, scripts/host/04-backup-ssd.sh images the SSD (about 8.7 GB, 7 minutes) with PhotonVision's settings inside. Keep that on the team drive too, never on GitHub: it holds the Wi-Fi password and SSH keys. And if cameras are stuck after a USB glitch, power-cycle the robot rather than pressing Reboot Device: a reboot doesn't cut the cameras' power (chapter 16).

Pipelines, profiles and driver mode

A pipeline is one saved set of settings for a camera: its type (AprilTagCuda, object detection…), exposure, resolution, detector settings. A camera can have several, numbered from 0, and runs one at a time. Robot code picks one with camera.setPipelineIndex(n), which goes over NetworkTables as pipelineIndexRequest.

Profiles are our habit of giving every camera the same pipelines at the same numbers: 0 = event field, 1 = practice field. Robot code then switches all cameras together, and the robot log records which one was active. Tune one camera's pipeline, then Copy settings (step 8) fills in the rest.

Driver mode is a pipeline that does no vision at all: it just sends a picture for the drivers. Pick Driver Mode in the Dashboard's pipeline list, or call camera.setDriverMode(true). Our build decodes those colour frames on the JPEG hardware, which about halves the CPU cost (1.12 → 0.59 cores at 120 fps).

// names must match PhotonVision exactly var topLeft = new PhotonCamera("TopLeft"); var topRight = new PhotonCamera("TopRight"); // profile: same number on every camera int profile = atEvent ? 0 : 1; // 0 = event, 1 = practice topLeft.setPipelineIndex(profile); topRight.setPipelineIndex(profile); // a camera just for the drivers driverCam.setDriverMode(true);
Don't borrow a tag camera

A camera in driver mode finds no tags. Switch an AprilTag camera to driver mode during a match and the robot loses that camera's poses until it switches back.
