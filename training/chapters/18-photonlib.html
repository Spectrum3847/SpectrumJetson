PhotonLib on the robot.

You've seen how the Jetson finds tags and works out where the robot is. This chapter is the other half: the Java you write on the robot to read those answers, aim with them, and feed them into the robot's position.

PhotonLib is PhotonVision's library for robot code. It subscribes to each camera's results over NetworkTables (chapter 15) and turns the bytes back into Java objects. You never talk to the Jetson directly: you make a camera object with the right name, and PhotonLib does the rest.

Our robot code (Spectrum3847/2026-FM-SystemCore, WPILib 2027 alpha-6 on the SystemCore) has no vision code yet. So everything here is "how to write it", checked against the exact PhotonLib version the robot uses.

Add the vendordep

PhotonLib v2027.0.0-alpha-2, and keep it there.

Make the cameras

new PhotonCamera("TopLeft"), one per camera, names exact.

Read every frame

getAllUnreadResults(), once per loop, per camera.

Use it

Aim at a tag (2D), or turn results into robot poses (3D).

Step 1: the vendordep, pinned

A vendordep is a JSON file in the robot project's vendordeps/ folder. It tells the build which library to download, and which version. In WPILib VS Code, open the WPILib sidebar, go to Vendor Dependencies, and install PhotonLib.

Then open vendordeps/photonlib.json and check the version says v2027.0.0-alpha-2. Never press "To Latest" on it.

Offline (at an event, no internet): download photonlib-v2027.0.0-alpha-2.zip from PhotonVision's GitHub releases ahead of time and unzip it into ~/wpilib/2027/vendordeps. It then shows up under the offline install.

Why alpha-2, and not newer

Our Jetson runs a 2026 PhotonVision (the only one with the CUDA detector). Every result it sends carries a fingerprint of its message layout, and PhotonLib compares it with its own every few seconds. For alpha-2 they match exactly (chapter 9).

Newer PhotonLib (after alpha-7) renamed the timestamp fields, so the fingerprint changes. Then the robot code throws an error and stops, with a banner that ends "Your code will now crash." (PhotonLib source). Stay in the alpha-6 era.

Java packages moved in WPILib 2027: geometry is org.wpilib.math.geometry, not edu.wpi.first.math.geometry, and the field layout is org.wpilib.vision.apriltag. Code copied from a 2025 or 2026 example needs its imports fixed. PhotonLib itself is still org.photonvision.

Step 2: one PhotonCamera per camera

A PhotonCamera is robot code's handle on one camera. You make it with the camera's name, and the name must match the name in the PhotonVision UI exactly, capitals included. It's the NetworkTables folder PhotonLib listens to: /photonvision/TopLeft/….

Ours are named after the USB port each camera is plugged into: TopLeft, TopRight, BottomLeft, BottomRight. (Every Thriftiest Cam reports the same serial number, so the port is the only way to tell them apart. Chapter 20 covers naming a new camera.)

Get the name wrong and nothing crashes. The Driver Station just says the camera was "not found on NetworkTables" and lists the camera names it can see, which is how you spot a typo. More in chapter 21.

// Once, when the robot starts
PhotonCamera topLeft     = new PhotonCamera("TopLeft");
PhotonCamera topRight    = new PhotonCamera("TopRight");
PhotonCamera bottomLeft  = new PhotonCamera("BottomLeft");
PhotonCamera bottomRight = new PhotonCamera("BottomRight");

// Handy extras on PhotonCamera
topLeft.isConnected();        // false if no results lately
topLeft.setPipelineIndex(1);  // switch pipeline
topLeft.setEnabled(false);    // rest while disabled

Step 3: read every frame

Each camera sends about 120 results a second. Robot code runs every 20 ms, 50 times a second. So between two loops, 2 or 3 new results pile up per camera.

getAllUnreadResults() hands you all of them, oldest first, and empties the pile. Loop over the list and use every one: more measurements means a steadier pose.

Two rules. Call it exactly once per loop per camera: a second call gets an empty list, because the first call already took everything. And call it every loop: the pile only holds 20 results (about 0.17 s at 120 fps), and older ones are thrown away.

The old getLatestResult() still exists, but it's marked deprecated for removal. It returns just the newest result, so at 120 fps it skips more than half the frames, and at low frame rates it hands you the same frame twice.

What's in a result

Each item in the list is a PhotonPipelineResult: everything one camera found in one frame. Always check hasTargets() first. getBestTarget() returns null when there are none, and using it then crashes the loop.

2D: aim at a tag

The simplest use needs no calibration and no field map: turn until the tag's yaw is 0. Yaw is how far off you are, so turn by an amount proportional to it. That's a P controller:

turn = kP × (0 − yaw)

The minus sign matters. Positive yaw means the tag is to the right, but a positive turn in WPILib is to the left. Get it backwards and the robot spins away from the tag.

Picking kP is a trade-off you can feel in the lab: too low and the robot creeps; too high and it swings past, comes back, and wobbles. The camera's delay makes the wobble worse, because the robot is always reacting to where the tag was.

// Every loop, while the driver holds the aim button
double turn = driverTurn;
for (var result : camera.getAllUnreadResults()) {
  if (!result.hasTargets()) continue;
  for (var t : result.getTargets()) {
    if (t.getFiducialId() == 10) {           // the tag we want
      turn = AIM_KP * (0 - t.getYaw()) * MAX_TURN_RAD_PER_S;
    }
  }
}
drivetrain.drive(forward, strafe, turn);   // latest result wins

The camera sees 81° across, like our Thriftiest Cams. If the tag leaves the view, there's no target and the robot stops turning. Real drivetrains also need a small minimum push to start moving, which this leaves out.

The offset camera trap

Yaw 0 means the camera points at the tag. If the camera sits 25 cm left of the robot's centre, the robot ends up parallel to that line, and its centre misses the tag by 25 cm at every distance. None of our four cameras is at the centre.

The fix: aim for a yaw that isn't 0. From the camera, a tag the robot's centre points at appears slightly right, by atan(offset / distance). That needs the distance, which is the next section. Or skip 2D entirely and aim from the robot's field pose (3D below): the pose estimator already knows where each camera is.

A camera mounted turned (yawed) has the same trap: yaw 0 then means the robot faces off by the mount angle. Add it to the setpoint.

2D: range from pitch

If the camera is at a fixed height and the tag's height is known, the tag's pitch gives the distance. It's the triangle from chapter 12: height difference ÷ tan(total angle up).

double tagZ = layout.getTagPose(10).get().getZ(); // 1.124 m
double meters = PhotonUtils.calculateDistanceToTargetMeters(
    0.45,                          // camera height, m
    tagZ,                          // tag centre height, m
    Math.toRadians(20),            // camera tilt, UP positive
    Math.toRadians(t.getPitch())); // target pitch, UP positive

Signature from PhotonLib alpha-2: (cameraHeightMeters, targetHeightMeters, cameraPitchRadians, targetPitchRadians). Careful: here a camera tilted up is positive, the opposite of Rotation3d in robotToCamera.

It works best when the tag is well above or below the camera. Our 2026 hub tags are at 1.124 m, but the wall tags are at 0.552 m. With a camera at 0.45 m that's a 10 cm difference, and a tiny pitch error becomes a huge distance error.

3D: where is the robot?

For driving anywhere on the field, you want the robot's field pose. PhotonPoseEstimator turns a result into one. It needs two things:

  • The field layout: where every tag is. Ours is the 2026 Rebuilt AndyMark layout, the same one the Jetson uses. WPILib's default field is the welded version, so name AndyMark explicitly.
  • robotToCamera: a Transform3d saying where the camera sits on the robot and which way it points. Chapter 19 shows how to measure it and get the signs right.

Then each result goes through a strategy method, and the answer goes to the drivetrain's pose estimator with its capture time and a trust level (chapter 12, chapter 14).

Method (alpha-2)What it doesUse it for
estimateCoprocMultiTagPoseUses the Jetson's multi-tag solve over every tag in view.First choice whenever 2+ tags are seen. Multi-tag must be on in the UI (ours is on by default).
estimateLowestAmbiguityPosePicks the single tag with the lowest ambiguity and solves from it.Fallback for one tag. Filter it (below).
estimateConstrainedSolvepnpPoseHolds heading to the gyro and solves position from all tags (like MegaTag2).Steady single-tag positions. Needs addHeadingData every loop (chapter 13).
estimatePnpDistanceTrigSolvePoseGyro heading plus the best tag's distance and direction.A cheap gyro-based solve from one tag.
estimateRioMultiTagPoseMulti-tag, but solved on the SystemCore.Rarely: the Jetson already does it.
estimateClosestToCameraHeightPose, …ClosestToReferencePose, …AverageBestTargetsPoseOther ways to choose between single-tag answers.Mostly older code.

In alpha-2 each strategy is its own method, and the only constructor is PhotonPoseEstimator(layout, robotToCamera). The old update() / setPrimaryStrategy style you'll see in older examples is gone. Every method returns an Optional: empty means "no answer from this frame".

Sanity filters every team needs

A bad vision pose can teleport the robot's estimate across the field in one frame. Three cheap checks catch nearly all of them before they reach the pose estimator:

On the field, on the floor

Reject a pose outside the field (16.52 × 8.04 m, plus a small margin), or more than about 25 cm above or below the floor. A robot can't be in the stands or flying.

No ambiguous single tags

With only one tag, reject it if getPoseAmbiguity() is above about 0.2. That's the flip from chapter 12. Multi-tag answers don't flip.

Trust falls with distance

Scale the standard deviations up with distance², down with more tags, and don't trust a single tag's heading at all. The starting rule: 0.01 × distance² ÷ tags² meters.

These numbers are starting points, not tuned values. PhotonVision computes ambiguity differently from Limelight, so thresholds carried over from old Limelight code need retesting (docs/LIMELIGHT-COMPARISON.md). Rewind recordings replayed through the robot code are the way to tune them.

Lessons from AOS's localizer (FRC 971's system, fixes merged July 2026)

AOS fuses vision on the coprocessor, but the bugs its maintainers fixed this summer apply to any pose estimator, including ours on the SystemCore:

  • Be stricter about heading resets in auto. Their localizer snapped its heading to vision during autonomous and landed badly. The fix: demand a much bigger heading disagreement before resetting in auto, and when it does reset, keep the current x and y instead of jumping to a delayed or noisy tag reading. For us: don't let vision reseed the pose in the middle of an auto path.
  • Don't blindly trust the controller's angular velocity. A bad turn-rate reading disagreed with the camera poses and kept triggering heading resets. Check the gyro against vision before letting either override the other.
  • Integrate odometry in the right order. They were applying newly received chassis speeds backwards over the interval before them. WPILib's estimators do this for you, but custom odometry threads can make the same mistake.
  • Watch for detections stopping. They added an "accepted tag count" so the robot notices when vision quietly stops contributing. Our robot code can count accepted measurements per camera itself, and our health topics (chapter 15) show fps and problems from the Jetson.
  • Gates that behave differently when disabled. A yaw-error gate that was too tight rejected good readings in auto-disabled but not teleop-disabled. Test every gate in every robot mode.

A complete vision subsystem

Here it all is for our four cameras: one camera and one estimator each, every unread result, multi-tag first, the three filters, then the drivetrain. It's about 60 lines. The mount numbers are made up; yours come from CAD or chapter 19.

public class Vision extends SubsystemBase {
  /** Where each camera sits: x fwd, y left, z up (m); roll, pitch, yaw (rad). Made-up numbers. */
  private static final Map<String, Transform3d> MOUNTS = Map.of(
      "TopLeft",     new Transform3d(0.28,  0.25, 0.45, new Rotation3d(0, Math.toRadians(-20), Math.toRadians(30))),
      "TopRight",    new Transform3d(0.28, -0.25, 0.45, new Rotation3d(0, Math.toRadians(-20), Math.toRadians(-30))),
      "BottomLeft",  new Transform3d(-0.28, 0.25, 0.40, new Rotation3d(0, Math.toRadians(-15), Math.toRadians(150))),
      "BottomRight", new Transform3d(-0.28, -0.25, 0.40, new Rotation3d(0, Math.toRadians(-15), Math.toRadians(-150))));

  /** Must match the Jetson's layout. WPILib's default is the WELDED field. */
  private static final AprilTagFieldLayout LAYOUT =
      AprilTagFieldLayout.loadField(AprilTagFields.k2026RebuiltAndymark);

  /** Usually drivetrain::addVisionMeasurement. */
  public interface Sink { void accept(Pose2d pose, double timestampSeconds, Matrix<N3, N1> stdDevs); }

  private final List<PhotonCamera> cameras = new ArrayList<>();
  private final List<PhotonPoseEstimator> estimators = new ArrayList<>();
  private final Sink sink;

  public Vision(Sink sink) {
    this.sink = sink;
    MOUNTS.forEach((name, robotToCamera) -> {
      cameras.add(new PhotonCamera(name));
      estimators.add(new PhotonPoseEstimator(LAYOUT, robotToCamera));
    });
  }

  @Override
  public void periodic() {
    for (int i = 0; i < cameras.size(); i++) {
      var estimator = estimators.get(i);
      for (var result : cameras.get(i).getAllUnreadResults()) {   // once per loop, every result
        var est = estimator.estimateCoprocMultiTagPose(result);   // 2+ tags
        if (est.isEmpty()) est = estimator.estimateLowestAmbiguityPose(result);  // 1 tag
        est.ifPresent(this::use);
      }
    }
  }

  private void use(EstimatedRobotPose est) {
    Pose3d pose = est.estimatedPose;
    int tags = est.targetsUsed.size();

    // 1. On the field, on the floor
    if (pose.getX() < -0.5 || pose.getX() > LAYOUT.getFieldLength() + 0.5
        || pose.getY() < -0.5 || pose.getY() > LAYOUT.getFieldWidth() + 0.5
        || Math.abs(pose.getZ()) > 0.25) return;

    // 2. A single tag must not be ambiguous
    if (tags == 1 && est.targetsUsed.get(0).getPoseAmbiguity() > 0.2) return;

    // 3. Trust falls with distance, rises with more tags
    double dist = est.targetsUsed.stream()
        .mapToDouble(t -> t.getBestCameraToTarget().getTranslation().getNorm())
        .average().orElse(10);
    double xy = Math.max(0.02, 0.01 * dist * dist / (tags * tags));
    double heading = tags > 1 ? xy * 2 : 1e6;   // one tag: ignore its heading

    sink.accept(pose.toPose2d(), est.timestampSeconds, VecBuilder.fill(xy, xy, heading));
  }
}

Written against PhotonLib v2027.0.0-alpha-2 and WPILib 2027 alpha-6 (SubsystemBase is in org.wpilib.command2, geometry in org.wpilib.math.geometry). Not yet run on our robot. Create it with new Vision(drivetrain::addVisionMeasurement).

Check the clock once

est.timestampSeconds is the capture time on the robot's clock, courtesy of time sync. WPILib 2027's pose estimator expects the clock of Timer.getMonotonicTimestamp(). On the first day with the robot, log Timer.getMonotonicTimestamp() - result.getTimestampSeconds(): it should be a small positive number, the latency (about 0.01 to 0.03 s). If it's huge or negative, the clocks don't match and every vision measurement lands at the wrong moment.

Adding the gyro (MegaTag2-style)

To use estimateConstrainedSolvepnpPose or estimatePnpDistanceTrigSolvePose, every estimator needs the gyro heading, every loop, so it can look up the heading at each frame's capture time:

// in periodic(), before reading results
for (var e : estimators) e.addHeadingData(Timer.getMonotonicTimestamp(), drivetrain.getHeading());

Chapter 13's "Pitfalls" box lists what bites in alpha-2: a missing heading can throw, the constrained solve costs CPU on the SystemCore (up to about 2 ms each), and it needs camera.getCameraMatrix() and getDistCoeffs(), which stay empty until the camera connects. A common plan: multi-tag to seed and check the heading, then the gyro-held solve for position.

CTRE swerve and other pose estimators

The Sink shape (Pose2d, double, Matrix<N3, N1>) matches WPILib's SwerveDrivePoseEstimator.addVisionMeasurement. CTRE's swerve drivetrain has a method with the same shape, but it keeps time on its own clock and wants the timestamp converted with Utils.fpgaToCurrentTime(...). Whichever you use, do the clock check above.

A turret camera needs one more step: before each estimate, call estimator.setRobotToCameraTransform(...) with the turret angle at the result's timestamp, not the current angle.

Simulation: VisionSystemSim

PhotonLib can fake the cameras in simulation. A VisionSystemSim holds the field's tags (addAprilTags(LAYOUT)). Each PhotonCameraSim wraps one of your real PhotonCamera objects, with SimCameraProperties describing it, and is added with the same robotToCamera. Call visionSim.update(simRobotPose) every sim loop, and your real vision code receives results as if the Jetson sent them.

var props = new SimCameraProperties();
props.setCalibration(1280, 800, Rotation2d.fromDegrees(91)); // ~diagonal FOV of our cams
props.setFPS(120);
props.setAvgLatencyMs(15);
visionSim.addCamera(new PhotonCameraSim(topLeft, props), MOUNTS.get("TopLeft"));

The upstream poseest example does exactly this. It's a good way to test filters and std devs before the robot exists.

Our extras on NetworkTables

Our PhotonVision publishes more than stock: per-camera health (/photonvision/TopLeft/health/fps, latencyMs, problem…), Jetson temperatures and throttling, settingsJson snapshots for the log, and controls like Rewind recording and excluded tags. Robot code reads them with plain NetworkTables subscribers and can raise Driver Station alerts from them. The full topic tree is in chapter 15.
